Hadur 3.2: R4 of the RoboRumble climb, a fallback that never stops fighting and the tooling
to keep chasing the lost live rounds.

**Download:** `hadur2.Hadur_3.2.jar`, or from the Google Drive link in the participant line at
the end. Robocode name `hadur2.Hadur 3.2`; runs on Java 11 or later. Enter it in both the
RoboRumble (1v1) and the MeleeRumble in place of 3.1: see
[docs/rumble-submission.md](https://github.com/lgriffin/Hadur_Robot/blob/master/docs/rumble-submission.md).

## Why this release exists

3.0's live rating collapsed at about 08:30 UTC on 2026-09-28, and 3.1 (R1 to R3) has not yet
accrued enough live pairings to say whether that touched it. R4 goes after the cause
directly: a client-conditions bench to try to reproduce the drop locally, a reader for the
live rating pages, and two changes that cap the damage of whatever it turns out to be,
whether or not it is ever reproduced locally. See
[docs/rumble-climb-r4-r6-plan.md](https://github.com/lgriffin/Hadur_Robot/blob/master/docs/rumble-climb-r4-r6-plan.md).

New since 3.1 (BENCH-4, BENCH-5, RES-7, RES-8; all merged in PR #67 and #68):

- **BENCH-4**, the client-conditions bench (`hadur-bench --client FILE`): runs the opponent
  set once per rumble-client condition a file lists — a shared or prefilled data directory,
  a forced CPU constant, background load, another engine or JVM — each its own pass,
  reporting survival share and skipped turns per opponent per condition.
- **BENCH-5**, the `LiveDetails` reader: turns a saved LiteRumble BotDetails page into a
  report by opponent-APS band, UTC hour, a before/after split and live-minus-bench share.
- **RES-7**: after three faulting ticks in a round, the guard's safe orders now also fire
  power 1.0 at the enemy's last scanned bearing whenever the gun is cool, instead of holding
  fire forever.
- **RES-8**: the core writes a small `health.hc` record at battle end (rounds, rounds
  survived, faults, skipped turns, memory failures, learned tick allowance), so a
  client-side reproduction of a live problem is self-describing.

## What R4b found

Run against this jar over the weak set, a shared never-wiped data directory, the CPU
constant forced to 1.0ms and to 0.3ms, and four background-load threads all leave survival
at 97 to 100%, unchanged from the default bench — none reproduces the live drop to 71-77%
survival. Neither does the plan's top candidate: a data directory built the way a real
client that has hosted every Hadur version would (2.2 warm over the weak set, then 3.0 warm
on top of it, 184 KB), with 3.2 prefilled from it. Another engine release, another JVM and
the actual offline RoboRumble client were not tried (no second engine, JDK or
`roborumble.jar` is available in this environment). See
[docs/bench/r4-client-conditions.md](https://github.com/lgriffin/Hadur_Robot/blob/master/docs/bench/r4-client-conditions.md),
[docs/bench/r4-prefill-condition.md](https://github.com/lgriffin/Hadur_Robot/blob/master/docs/bench/r4-prefill-condition.md)
and `data/learnings.md` L-21. Per the plan's decision tree, this release ships the fallback
(RES-7/RES-8) anyway and reads the live rating with BENCH-5 once 3.2 has 300+ pairings,
rather than block on conditions this environment cannot exercise.

**Timing:** 3.1 went live at 04:32 UTC 2026-09-29; the plan's read on whether R1 already
cured the collapse needs 3.1's own BotDetails page with 300+ pairings (about 6 hours, so
from roughly 10:30 UTC). Save that page before swapping the live entry to 3.2, or that
signal is lost.
