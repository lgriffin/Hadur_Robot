# Tag the JUnit tests

JUnit 5 has `@Tag`: a label on a test method or a class. We use it for the requirement ID:

```java
import org.junit.jupiter.api.Tag;

@Test
@Tag("HL-3")
@DisplayName("the radar overshoots the enemy to keep it in view")
void radarOvershoots() { ... }
```

A tag is not just documentation. Maven can run by tag (`-Dgroups=HL-3`), and our traceability test reads
the text `@Tag("HL-3")`. Put it on the line above the method, in this exact form.

A test may serve several requirements, and a requirement may have several tests. A requirement
that depends on a random choice of inputs gets a property:

```java
import net.jqwik.api.Tag;

/**
 * Round trips: whatever we write, we read back equal. The generators are the interesting part:
 * they include NaN, infinities, negative zero and names full of separators, which is exactly
 * what a hand-written example would forget.
 */
@Tag("HL-8")
class LineCodecProperties {
```

## The jqwik trap

Look at the import: `net.jqwik.api.Tag`, **not** `org.junit.jupiter.api.Tag`. jqwik tests run on a
different engine, and it ignores JUnit's `@Tag` annotations by *skipping the test*, without
saying a word. A property that quietly never runs is worse than none, because the traceability
test would count it as coverage. Our test in step 5 includes a check for exactly this mistake.

On a class, a tag applies to every test in it. That is why `@Tag("HL-8")` goes above
`class LineCodecProperties`.
