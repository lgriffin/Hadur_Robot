# Exercises

## 1. A ninth requirement, test first

Write `HL-9`: *If the enemy is not scanned for more than two ticks, then the core shall order the
radar to sweep.* Add it to the table, run the build and see it go red, write a `CoreTest` test tagged
`HL-9` (the sweep logic exists already: check it with ticks 1 and 5), and watch it go green.

## 2. A scenario for HL-5

Write a Cucumber scenario tagged `@HL-5`: *Given* the core is driving forwards, *When* the robot
hits a wall, *Then* the next orders drive backwards. You need new step definitions. Keep the
`Core` object in a field so the two ticks share state.

## 3. Report who is least covered

Extend `writeReport()` so the table also has a column with the number of tests (tag occurrences)
per requirement, and prints a warning to `System.out` for any requirement with exactly one. Is
that useful? What does it miss? (Hint: one test can be a great test.)

## 4. Stages

Hadur's table has a fifth column, the *stage* a requirement belongs to, and the test only
insists on requirements due at or before the current stage. That lets a plan list future
requirements without failing the build. Add a `Stage` column (`S1`, `S2`) to your table, a Maven
property `hadurling.stage` handed to the tests as a system property, and make only due
requirements count as missing. Where must unknown tags still fail?
