# The bench module

Add a third module to the parent `pom.xml`:

```xml
<modules>
    <module>hadurling-core</module>
    <module>hadurling-robot</module>
    <module>hadurling-bench</module>
</modules>
```

## The engine from Maven Central

Robocode's full engine is published on Maven Central. The bench's `pom.xml` depends on
`robocode.api` (already used by the robot) and on `robocode.core`, `robocode.host`,
`robocode.battle` and `robocode.repository`, all at the same version (1.9.5.6), plus
`robocode.samples` for the sample opponents. There is nothing to download by hand.

Two Maven plugin executions help the bench:

- `build-classpath` writes the runtime classpath to `target/classpath.txt`. The bench needs it
  because it starts child JVMs and must tell them where the classes are.
- `copy` puts the samples jar in `target/samples`, so each battle's Robocode home can have it.

The bench compiles at Java 17, because it never ships to RoboRumble; the robot stays at Java 11.

## One battle, one JVM

`BattleRunner` is a `main` that fights one battle and writes one line:

```java
RobocodeEngine engine = new RobocodeEngine(home);
...
RobotSpecification[] robots = engine.getLocalRepository(us + "," + them);
engine.runBattle(new BattleSpecification(rounds, new BattlefieldSpecification(width, height), robots), true);
...
Files.writeString(result, scores[0] + "," + scores[1] + "\n");
```

It listens for `onBattleCompleted` to read the scores, and writes `ERROR ...` to the result file
if the engine reports a problem or the wrong number of robots turns up. It ends with
`System.exit`, because the engine leaves threads running.

`Bench` starts it once per battle:

```java
cmd.add(Path.of(System.getProperty("java.home"), "bin", "java").toString());
cmd.addAll(JVM_FLAGS);
cmd.add("-DRANDOMSEED=" + seed);
cmd.add("-cp");
cmd.add(classpath());
cmd.add(BattleRunner.class.getName());
cmd.addAll(List.of(home.toString(), result.toString(), String.valueOf(rounds), field[0], field[1],
    robot, opponent));
```

`-DRANDOMSEED=<seed>` is the reason for the child JVM, as step 1 said: Robocode reads it once.

`JVM_FLAGS` opens some JDK internals that Robocode reaches into, and keeps **the security manager
on** (`-Djava.security.manager=allow`), as in a real Robocode install. The security manager is what
stops a robot from writing outside its data directory, so a bench without it would measure a robot
that cheats. Java 18 and later turn it off by default and Java 24 removes it, so **use a JDK from 17
to 21** to run the bench.

## Cold and warm

Hadurling now remembers opponents between battles (lab 10). So the bench has a choice. The default is
**cold**: before each battle it wipes the robot's data directory, so every battle stands alone and
a number means "against a stranger". With `--warm` the data is kept, and later battles start with
what earlier ones taught. Use cold to compare versions and warm to see learning.

## Options

| Option | Meaning |
|--------|---------|
| `--opponent A,B` | opponents by name (default `sample.Crazy`) |
| `--opponent-jar X.jar,Y.jar` | robot jars of your own to install so `--opponent` can name them |
| `--rounds N` | rounds per battle (default 35) |
| `--seeds N` | battles per opponent, seeds 1 to N (default 5) |
| `--field WxH` | battlefield (default 800x600) |
| `--warm` | keep the robot's data between battles |
| `--robot-jar FILE` | the robot to measure |
| `--baseline-jar FILE` | an older jar to compare against, on the same seeds |
| `--baseline-name`, `--candidate-name` | labels in the A/B table |
| `--out DIR`, `--report FILE` | working folder and a file for the report |

`BattleRunner` and the child-process code stay out of the unit tests on purpose: they need a real
engine. What is left in `ReportTest` is the part you can test: option parsing (`--warm` is a flag,
everything else is a key and a value), and turning a result file into a share.

```java
static double readShare(Path result) throws IOException {
    if (!Files.exists(result)) throw new IOException("no result file " + result);
    String line = Files.readString(result).trim();
    if (line.startsWith("ERROR")) throw new IOException(line);
    ...
    return ours + theirs == 0 ? 0.5 : ours / (ours + theirs);
}
```

An error file stops the bench with a message. A battle that failed must never become a score of 0%.
