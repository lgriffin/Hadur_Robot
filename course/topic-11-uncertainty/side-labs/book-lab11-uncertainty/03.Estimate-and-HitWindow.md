# Estimate and HitWindow

## The interval

There are several ways to compute a confidence interval for a rate. The simple textbook one
(`p +- 1.96 * sqrt(p(1-p)/n)`) breaks down exactly where we need it: with few samples, or a rate
near 0 or 1. With 0 hits from 10 it says the margin is zero, which is absurd. Hadurling uses the
**Agresti-Coull interval**. Add two hits and two misses to what you saw, and then use the textbook
formula:

```
p      = (hits + 2) / (n + 4)
margin = 1.96 * sqrt(p * (1 - p) / (n + 4))
```

The interval is `center +- margin`, where the center is `p`. That is the interval, so say it in the
class comment. "A 95% margin" is not enough; the reader has to know which one.

Create `hadurling/core/policy/Estimate.java`:

```java
public static Estimate of(double hits, double n) {
    // Written as !(x > 0) rather than x <= 0 so that NaN is rejected too.
    if (!(n > 0) || Double.isInfinite(n) || !(hits >= 0) || Double.isInfinite(hits)) return NONE;
    double h = Math.min(hits, n);
    double p = (h + 2) / (n + 4);
    return new Estimate(h / n, 1.96 * Math.sqrt(p * (1 - p) / (n + 4)), n);
}
```

Two values, on purpose. `value()` is the raw rate `h / n`, which is what a person expects to see.
`center()` is the adjusted `p`, and `lower()` and `upper()` are measured from the center:

```java
public double lower() { return center - margin; }
public double upper() { return center + margin; }
```

`NONE` is the estimate of nothing: a rate of NaN and a margin of 1, which is requirement `HL-25`.
Bad input (negative, NaN, infinite) is `NONE` too, never an exception. A policy that reads it will
find "unknown" and hold back.

`EstimateTest` pins it down, tagged `HL-25`:

- with no samples nothing is known: no rate, a margin of 1
- the margin is exactly the Agresti-Coull formula (check one hand-computed number)
- a perfect or empty record over a few shots still has a wide margin
- more samples narrow the margin
- hits above the trials are clamped, so the rate never passes 1

## The window

`HitWindow` is a ring buffer of booleans. A new outcome overwrites the oldest:

```java
public void record(boolean hit) {
    if (size == outcomes.length) {
        if (outcomes[next]) hits--; // the slot about to be overwritten holds the oldest
    } else {
        size++;
    }
    outcomes[next] = hit;
    if (hit) hits++;
    next = (next + 1) % outcomes.length;
}

public Estimate estimate() {
    return size == 0 ? Estimate.NONE : Estimate.of(hits, size);
}
```

It never counts the whole array: it keeps `hits` up to date as it goes. That is faster, and it is
also how bugs get in. The bookkeeping must agree with the truth, so test it against the truth.

```java
@Tag("HL-26")
class HitWindowProperties {

    @Property
    void windowEqualsTheLastNOutcomes(@ForAll @IntRange(min = 1, max = 30) int capacity,
            @ForAll @Size(max = 200) List<Boolean> outcomes) {
        HitWindow window = new HitWindow(capacity);
        for (boolean o : outcomes) window.record(o);

        List<Boolean> last = outcomes.subList(Math.max(0, outcomes.size() - capacity), outcomes.size());
        long hits = last.stream().filter(b -> b).count();
        Estimate expected = last.isEmpty() ? Estimate.NONE : Estimate.of(hits, last.size());

        assertEquals(last.size(), window.size());
        assertTrue(window.size() <= capacity);
        assertEquals(expected.value(), window.estimate().value(), 1e-12);
        assertEquals(expected.margin(), window.estimate().margin(), 1e-12);
    }
}
```

The slow way: take the last `capacity` outcomes of the list, count them, build an `Estimate`. The
fast way: the ring buffer. The property says they always agree. It is the same model-based idea as
the k-d tree in lab 08.

`Evidence` is two windows (ours and theirs) and the name of the opponent they are about. When
`against(key)` is called with a new opponent it clears both. That keeps one opponent's record from
being used on another.
