# The tick, and why values

## What happens in a tick

Each tick, the engine does this for your robot:

1. It moves everything one step and works out what happened: a scan, a hit, a wall.
2. It calls your event handlers (`onScannedRobot` and friends), one per event.
3. It lets your `run()` loop go on until `execute()` is called again.

Today Hadurling decides inside step 2: `onScannedRobot` reads the event and calls
`setTurnRight`, `setFire` and so on directly. This works. It also means that to test any decision
you need a running battle, and to understand one you must read engine calls and strategy mixed
together.

## The shape we want

```text
engine events ──▶  Input  ──▶  Brain  ──▶  Orders  ──▶  engine calls
 (adapter)       (a value)   (decides)    (a value)     (adapter)
```

The only things that cross the line between the engine and the brain are **values**: plain
objects that hold data and do nothing. A value has no side effects and never changes. If you
give the brain the same `Input` twice it must give the same `Orders` twice, which makes it
trivially testable, and, in Lab 06, replayable.

## Rules for our values

- **Immutable.** All fields `final`; no setters. Once built, it never changes.
- **Defensive copies.** If a value holds a list that its caller can still change, the value is
  not really immutable. Copy it on the way in.
- **Value equality.** Two `Input`s with the same contents are equal, so tests can compare them
  with `assertEquals`.
- **No Robocode types inside.** Angles are radians, distances px: plain `double`s.

Java 17 has `record` for this. Hadurling's main code targets Java 11 (Robocode clients still run
it), so we write the boilerplate by hand and learn what a record would generate.
