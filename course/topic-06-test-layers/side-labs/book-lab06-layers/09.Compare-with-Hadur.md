# Compare with Hadur

The record-and-replay layer arrived with the hexagon, in stage S1:

- [`replay/LineCodec`](https://github.com/lgriffin/Hadur_Robot/blob/afd6cc9/hadur-core/src/main/java/hadur2/core/replay/LineCodec.java):
  your codec, with the same `I`/`O` lines, the same `%XX` escapes and the same promise ("reads
  back to the same bits"). It has more event letters and optional trailing fields, so
  recordings from older versions still read. Compare the class comment with step 2.
- [`replay/Replay`](https://github.com/lgriffin/Hadur_Robot/blob/afd6cc9/hadur-core/src/main/java/hadur2/core/replay/Replay.java):
  your `Replay`; a new core per `R` line, the guard in the loop, a `Tick` that holds recorded and
  replayed orders (it uses a `record`, the Java 17 way).
- [`ReplayTest`](https://github.com/lgriffin/Hadur_Robot/blob/afd6cc9/hadur-core/src/test/java/hadur2/core/replay/ReplayTest.java):
  your `ReplayTest`, run over recordings of **real battles** against `sample.SpinBot`,
  `sample.Tracker`, `sample.Crazy`, `sample.Walls`, `sample.RamFire` and another top robot, in
  `src/test/resources/replay/*.txt.gz`. It also checks a fixture exists for every reference
  opponent, and runs each replay twice.
- [`LineCodecProperties`](https://github.com/lgriffin/Hadur_Robot/blob/afd6cc9/hadur-core/src/test/java/hadur2/core/replay/LineCodecProperties.java):
  round-trip properties with generators.
- [`BulletShadowsProperties`](https://github.com/lgriffin/Hadur_Robot/blob/a9ee021/hadur-core/src/test/java/hadur2/core/move/BulletShadowsProperties.java):
  a *model-based* property like exercise 2, where fast code is checked against a brute-force
  one.
- [`docs/testing.md`](https://github.com/lgriffin/Hadur_Robot/blob/a9ee021/docs/testing.md),
  sections "The layers" and "Replay fixtures": the table of layers with what each catches, and how
  fixtures are recorded and kept.

## Notice

1. **Real fixtures are recorded by the bench**, not by hand, and they are gzipped. The idea is
   yours; the pipeline is just bigger.
2. **Fixtures are why the strategy could change fast.** When a stage changed the duel on purpose,
   it re-recorded; when a refactor was meant to change nothing, the fixtures proved it.
3. **Layers, again.** Find the table in `testing.md` and match each of its rows to a class in the
   Hadur repository.

Lab 07 adds the layer that ties tests back to requirements.
