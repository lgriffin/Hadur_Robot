# The layers

Different tests catch different mistakes. Here is what you have, and what this lab adds:

| Layer | Question it answers | You have |
|---|---|---|
| Architecture | Is the code shaped as designed? | `ArchitectureTest` (Lab 05) |
| Unit | Does this class do what I thought on my examples? | `AnglesTest`, `CoreTest`, `GuardTest` |
| Property | Does this rule hold for **every** input? | `AnglesMatchEngineProperties` (Lab 02); `LineCodecProperties` (now) |
| Replay | Did the **whole** core's behaviour change on a real battle? | `ReplayTest` (now) |
| Behaviour | Does it do what the requirements say? | Lab 07 |
| Traceability | Is every requirement tested? | Lab 07 |

Hadur adds more at the bottom: an adapter layer (the real Robocode engine) and a bench (hundreds of
battles, a score). Those come in Topic 12.

## How the layers complement each other

- A unit test checks the cases you thought of. It cannot check the ones you did not.
- A property tests a rule over thousands of cases, including the nasty ones. It cannot tell
  you the robot's overall behaviour has quietly changed.
- A replay does exactly that: if any change in the core alters any order on a recorded battle,
  it fails. But it cannot tell you *which* rule you broke. The unit tests and properties do.

None of them is enough. Used together they leave few places to hide.

## Today's feature carries both

To replay a battle, the battle must be written down. We need a **text form** of an `Input` and
of `Orders`, a way to write each to one line and read it back without losing a bit. That codec
is itself worth a property: *whatever you write, you can read back equal*. A broken codec would
make every replay pass or fail for the wrong reason.
