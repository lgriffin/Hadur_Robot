# Lab 05: Guardrails in the build

A module boundary stops the core importing Robocode. It cannot stop someone adding
`new Random()`, a thread, a file write or a call to the system clock. Each of those makes the
core's answers depend on something other than its `Input`, and so breaks the promise that the same
input gives the same orders. In this lab you turn those promises into tests that fail the build.

## Objectives

By the end of this lab you can:

- write ArchUnit rules about dependencies, calls and packages
- explain why determinism matters for replay, tests and debugging
- break each rule on purpose and read the failure message
- write a determinism test that runs the same inputs through two cores

## What you start from

`course-labs/lab-04`, or this lab's [`start.zip`](./archives/start.zip).

## What you will have at the end

- `ArchitectureTest`: seven ArchUnit rules over the compiled core
- `DeterminismTest`: the same inputs twice give the same orders
- `archunit-junit5` 1.3.0 in the parent pom and the core pom
- no change to the main code; the rules describe what it already respects

This is `course-labs/lab-05`.
