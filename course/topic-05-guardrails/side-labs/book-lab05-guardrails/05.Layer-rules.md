# Rules about layers

Draw the packages as layers. The bottom ones are used by all the others:

```text
        core (Core, Guard)
        /     \
     gun      move        (neither knows the other)
        \     /
     model, physics       (know nothing above them)
```

Two rules keep the picture true:

```java
    @Test
    @DisplayName("the model and the physics do not depend on the gun or the movement")
    void layering() {
        noClasses().that().resideInAnyPackage("hadurling.core.model..", "hadurling.core.physics..")
            .should().dependOnClassesThat().resideInAnyPackage("hadurling.core.gun..", "hadurling.core.move..")
            .check(core);
    }

    @Test
    @DisplayName("the gun and the movement do not depend on each other")
    void gunAndMoveAreIndependent() {
        noClasses().that().resideInAPackage("hadurling.core.gun..")
            .check(core);
    }
```

If the gun needed something from the movement, you would be tempted to import it. The rule
makes you stop and ask whether the shared thing belongs lower down, in `model` or `physics`, or
whether the `Core` should pass it to both. Both are better designs than a hidden coupling.

The pattern, "A may depend on B, B may not depend on A", is the **dependency rule**. It is the
single most useful architectural rule there is. Dependencies that only point one way can be
understood one layer at a time.

Each rule here is one test. Count them: seven.
