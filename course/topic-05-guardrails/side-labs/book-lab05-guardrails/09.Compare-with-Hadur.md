# Compare with Hadur

Hadur's rules live in one test class, from the S1 rebuild:

- [`ArchitectureTest`](https://github.com/lgriffin/Hadur_Robot/blob/afd6cc9/hadur-core/src/test/java/hadur2/core/arch/ArchitectureTest.java):
  your seven rules and a few more. Find `coreHasNoRobocode`, `noRandomness`, `noThreads`, `noIo`,
  `layering` and `gunAndMoveIndependent`: they are your rules. Look at what else is there:
  no reflection, no mutable statics, a check that the core uses only the JDK.

Notice that most rules carry `@Tag("CORE-1")`, `@Tag("RES-6")` and similar. Those are
requirement IDs, and Lab 07 is about them: a rule that is also a requirement is traced.

One test in the real project goes further than anything you wrote:

- [`DuelIdentityTest`](https://github.com/lgriffin/Hadur_Robot/blob/a9ee021/hadur-core/src/test/java/hadur2/core/arch/DuelIdentityTest.java):
  the duel code is **pinned by a hash**. A later change that added melee play to Hadur had to
  leave the 1v1 sources exactly as they were, and this test fails if even one byte of them changes.
  It is a rule about *the code*, not about structure.

The whole testing approach, with a table of all layers, is described in
[`docs/testing.md`](https://github.com/lgriffin/Hadur_Robot/blob/a9ee021/docs/testing.md),
sections "The layers" and "The duel is pinned".

## Notice

1. **Rules have names and reasons.** `RES-6` is "no unseeded randomness, threads, reflection or file I/O in the core". The ID
   leads to a sentence in `docs/requirements.md` that says why.
2. **The rules were written before the code needed them.** They were in the S1 commit, with the
   hexagon, so no later change could slip past.
3. **Javadoc is also checked**: Hadur's build runs doclint, so a broken `{@link}` fails like a
   test. The same idea, a different tool.
