# The adapter and the jar

## The robot module

`Hadurling` stays in `hadurling-robot`. It now imports from `hadurling.core...`, and builds a
`Core` and a `Guard` for each round. The changed parts:

```java
        Core core = new Core();
        guard = new Guard(core::tick, line -> out.println(line));
        guard.newRound();

        while (true) {
            Input in = input();
            apply(guard.tick(in));
            execute();
        }
```

- `core::tick` is the method reference; `line -> out.println(line)` is a `Telemetry` lambda. The
  robot's console `out` is the one thing the core never touches; the adapter lends it through the
  port.
- The loop calls `guard.tick(in)`, never `core.tick(in)`. The guard is the only door.

Update the imports (`hadurling.core.Core`, `hadurling.core.Guard`, and the `...core.model`
types) and remove the old `Brain` field.

## One jar per robot

Robocode loads a robot from **one jar**. But our robot class is in `hadurling-robot` and the core
is a separate jar, `hadurling-lab04-core`. If we shipped only the robot's own jar, the first
`new Core()` would fail with `NoClassDefFoundError`. The **Maven shade plugin** copies the
dependency's classes into the robot's jar:

```xml
    <build>
        <!-- Robocode's naming: package.RobotName_version.jar -->
        <finalName>hadurling.Hadurling_${project.version}</finalName>
        <plugins>
            <!-- Robocode loads one jar per robot, so the core is copied into the robot's jar. -->
            <plugin>
                <groupId>org.apache.maven.plugins</groupId>
                <artifactId>maven-shade-plugin</artifactId>
                <version>3.6.0</version>
                <executions>
                    <execution>
                        <id>robot</id>
                        <phase>package</phase>
                        <goals>
                            <goal>shade</goal>
                        </goals>
                        <configuration>
                            <createDependencyReducedPom>false</createDependencyReducedPom>
                            <artifactSet>
                                <includes>
                                    <include>course.hadurling:hadurling-lab04-core</include>
                                </includes>
                            </artifactSet>
                        </configuration>
                    </execution>
                </executions>
            </plugin>
        </plugins>
    </build>
```

Read the three important parts:

- `<finalName>` follows Robocode's naming rule, `package.RobotName_version.jar`.
- `<phase>package</phase>`: it runs when the jar is made.
- `<artifactSet><includes>`: only the core is copied in. The Robocode API is `provided`, so the
  engine supplies it, and it is not packed.

The properties file stays in `src/main/resources/hadurling/`, so Robocode can find it.

Test it: a small test makes sure the robot's properties file names a class that exists and that
extends `AdvancedRobot`:

```java
package hadurling;

import static org.junit.jupiter.api.Assertions.assertEquals;
import static org.junit.jupiter.api.Assertions.assertNotNull;

import java.io.InputStream;
import java.util.Properties;
import org.junit.jupiter.api.DisplayName;
import org.junit.jupiter.api.Test;
import robocode.AdvancedRobot;

/** Robocode finds a robot through its .properties file, so a typo there loses the robot. */
class RobotPropertiesTest {

    @Test
    @DisplayName("the properties file names a loadable AdvancedRobot")
    void propertiesNameTheRobot() throws Exception {
        Properties p = new Properties();
        try (InputStream in = getClass().getResourceAsStream("/hadurling/Hadurling.properties")) {
            assertNotNull(in, "hadurling/Hadurling.properties is missing");
            p.load(in);
        }
        assertEquals("hadurling.Hadurling", p.getProperty("robot.classname"));
        Class<?> robot = Class.forName(p.getProperty("robot.classname"));
        assertEquals(true, AdvancedRobot.class.isAssignableFrom(robot));
    }
}
```

A typo in the properties file would otherwise lose the robot in Robocode with no message. Now
the build catches it.
