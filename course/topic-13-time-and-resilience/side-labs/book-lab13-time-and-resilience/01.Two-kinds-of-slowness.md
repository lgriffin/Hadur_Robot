# Two kinds of slowness

## The tick

In a real battle Robocode gives every robot a fixed amount of CPU time per turn. If a robot's code is
still running when the turn ends, the engine **skips the turn**: the robot's orders for that tick
do not happen. Skip several in a row and the gun stops tracking or the robot drives into a wall.
Faster machines hide the problem, and slower ones (such as the rumble clients) show it. So a robot
needs two things: a way to know it is running long, and something to give up when it is.

## The slide

Lab 10 gave the robot a memory of every opponent it has met. Lab 10's way of saving a profile made
room for it by listing all files in the store and asking each for its size. With ten profiles that
is nothing. With a thousand, every save lists a thousand files, and a robot that has fought many
opponents gets slower and slower. A cost that grows with the data is called a slide, because the
robot slides down a slope you did not see at the top. Both of these are the same lesson: **find the
thing that grows and measure it.**

## Write the requirements

| ID | Pattern | Requirement |
|----|---------|-------------|
| HL-36 | Event-driven | When the previous tick used more than 70% of the time allowance, the tick budget shall shed one computation level for this tick only. |
| HL-37 | Event-driven | When the engine skips a turn, the tick budget shall shed one computation level for the rest of the round, down to level 3. |
| HL-38 | State-driven | While the level is 1 or more the gun shall ask the tree for half as many neighbours; at 2 or more the surfer shall not predict; at 3 the gun shall aim head-on. |
| HL-39 | Ubiquitous | The core shall not read a clock; the adapter shall time each tick and report it as an event on the next. |
| HL-40 | Ubiquitous | The profile library shall list the store once per battle and keep an index, so that no save does work proportional to the number of files in the store. |
| HL-41 | State-driven | While the store is full, the library shall forget the least recently written other profiles, found from the index, until the save fits. |

`HL-36` and `HL-37` are different on purpose. A slow tick is a hint, so it costs one level for one
tick. A skipped turn is a fact (the engine is telling you), so it costs a level for the rest of the
round.

`HL-39` is a requirement about **where** a decision is made. The core is pure and replayable, so it
may not read a clock. The adapter reads it and tells the core.

`HL-40` has a clause that is easy to miss: "no save does work proportional to the number of files".
It is a statement about growth, and it is testable without a stopwatch. You will see how in step 6.
