# Count the listings

How do you test that a cost does not grow? The obvious way is to time it, and it is the wrong one.
A timing test passes on a fast machine and fails on a slow one, and it fails at random. Count
instead the **thing that grows**: how often the library asks the store to list itself.

## A counter in the fake

`MemoryProfileStore` counts how often `names()` is called:

```java
public List<String> names() {
    listings++;
    return new ArrayList<>(entries.keySet());
}

public int listings() {
    return listings;
}
```

`FileProfileStore` gets the same counter (package-private, for its own test), because on a real
disk a listing is a directory scan.

## The scale tests

`ProfileLibraryScaleTest`, tagged `HL-40` and `HL-41`:

```java
@Test
@Tag("HL-40")
@DisplayName("300 saves into a store that already holds 300 profiles list the store once")
void oneListingForHundredsOfSaves() {
    MemoryProfileStore store = new MemoryProfileStore(10_000_000);
    for (int i = 0; i < 300; i++) {
        String key = "old.Bot" + i;
        store.write(ProfileLibrary.fileFor(key), ProfileCodec.encode(profile(key)));
    }
    ProfileLibrary library = new ProfileLibrary(store);
    for (int i = 0; i < 300; i++) assertTrue(library.save(profile("new.Bot" + i)));
    assertEquals(1, store.listings());
    assertEquals(600, store.names().size());
}
```

Read the numbers. Three hundred profiles are already there. Three hundred more are saved. The store is
listed **once**. Under the lab 12 method that would be 300 listings, each with 300 to 600 size calls.

The other tests:

- **as the store grows to 800 profiles the number of listings does not grow with it.** Record the
  count at 200, 400, 600 and 800 saves: it must be 1, 1, 1, 1. This is the shape of
  `HL-40`: a statement about growth, tested at several sizes.
- **loading never lists the store** (`HL-40`)
- **after a failed save the library no longer trusts its index and lists again** (`HL-40`): crash a
  write with `crashOnWrite`, and the count goes to 2, not 3, and the next load still works
- **when the store is full the oldest profile goes, found from the index** (`HL-41`)

`FileProfileStoreScaleTest` does the same with real files in a temporary folder: 300 saves into a
folder that already holds 300 profiles scan the folder once.

## The index must be right as well as fast

An index that is fast and wrong would pass every count. So the lab keeps the old algorithm and tests
the new one against it, the same model-based property you wrote for the k-d tree in lab 8:

```java
/** What lab 10's makeRoom did, kept as the obviously-right model: list everything, every time. */
private static boolean naiveSave(MemoryProfileStore store, Profile profile) { ... }

@Property
@Tag("HL-41")
void theIndexedLibraryForgetsWhatThePlainOneForgot(@ForAll("saves") List<Profile> saves,
        @ForAll("quotas") int quota) {
    MemoryProfileStore plain = new MemoryProfileStore(quota);
    MemoryProfileStore indexed = new MemoryProfileStore(quota);
    ProfileLibrary library = new ProfileLibrary(indexed);
    for (Profile p : saves) {
        boolean a = naiveSave(plain, p);
        boolean b = library.save(p);
        assertEquals(a, b, "save of " + p + " differed");
        assertEquals(plain.names(), indexed.names(), "after saving " + p);
    }
}
```

Any run of up to 40 saves of 12 different robots with seeds of different sizes, into any quota from
300 to 4000 bytes: both libraries must agree on whether each save worked and on which profiles are
left. The slow version is the specification of the fast one.

## See the slide with your own eyes

The tests do not time anything. To see the difference in milliseconds, run the demo, which is not
a test and is not run by `mvn verify`:

```sh
mvn -B -q test-compile dependency:build-classpath -pl hadurling-robot -am -Dmdep.outputFile=target/cp.txt
cd hadurling-robot
java -cp target/classes:target/test-classes:$(cat target/cp.txt) hadurling.SlideDemo 1500
```

It saves 1500 profiles into a real folder, twice, and prints the time for each hundred saves. The
author's run: the list-every-time column grew from about 70 ms to about 575 ms per hundred saves,
while the indexed column stayed between 10 and 30 ms. Your numbers will differ. The shape will not.
