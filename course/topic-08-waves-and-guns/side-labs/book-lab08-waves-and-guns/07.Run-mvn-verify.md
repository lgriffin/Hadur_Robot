# Run `mvn verify`

```sh
cd course-labs/lab-08
mvn -B verify
```

Expect `BUILD SUCCESS`. Along the way you should see:

- `KdTreeProperties` run as a jqwik property, with many generated tries
- the traceability test pass for `HL-1` to `HL-13`
- the ArchUnit tests pass, including two new rules

## The two new ArchUnit rules

```java
@Test
@DisplayName("knn is a leaf: it depends on nothing of Hadurling's")
void knnIsALeaf() {
    classes().that().resideInAPackage("hadurling.core.knn..")
        .should().onlyDependOnClassesThat().resideInAnyPackage("hadurling.core.knn..", "java..")
        .check(core);
}
```

A second rule says that only the gun uses the tree. A new package gets its rules the day it is
born, while its shape is still clear in your head.

## The replay fixture has to change

Now the replay test will probably fail, and that is correct. The robot's play has changed on
purpose: it now fires waves and reacts to enemy energy drops, so its orders for the same recorded
battle are different. Look at the failure and make sure you can explain why the orders differ. Then
regenerate the fixture:

```sh
mvn -B test-compile
java -cp hadurling-core/target/classes:hadurling-core/target/test-classes \
  hadurling.core.replay.ScriptedBattle hadurling-core/src/test/resources/replay/scripted-duel.txt
```

In this lab `ScriptedBattle` also gained enemy energy drops and one hit by our bullet, so the script
exercises the new code. Commit the new fixture with a message that says the play changed on purpose.
A fixture that changes by accident is a bug. A fixture that changes on purpose is a decision, and
the commit message is where you record it.

Run `mvn -B verify` again and expect green.

## What if it does not pass?

- **Traceability fails.** Read which `HL-n` it names. Either a row has no tagged test or a tag
  names a row that does not exist.
- **A jqwik property never ran.** Check the import is `net.jqwik.api.Tag`.
- **ArchUnit complains about `knn`.** Something in the tree imports a Hadurling class. Move it out.
