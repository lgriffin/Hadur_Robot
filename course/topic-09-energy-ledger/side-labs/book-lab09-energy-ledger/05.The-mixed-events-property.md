# The mixed-events property

Examples check the combinations you thought of. A property checks the ones you did not. The idea:
**build a battle where you know exactly what happened, hand the ledger only the symptoms, and
require it to recover the truth.**

Create `EnergyLedgerProperties` in the `ledger` test package, tagged `HL-14`, with jqwik's `Tag`.

## The truth

```java
record Interval(double shot, List<Double> ourHits, List<Double> theirHits, boolean wall, double speed) {
    double energyChange(double wallDamage) {
        double change = -shot;
        for (double p : ourHits) change -= Rules.bulletDamage(p);
        for (double p : theirHits) change += 3 * p;
        return change - wallDamage;
    }
}
```

An `Interval` is everything that really happened between two scans: whether the enemy fired (0 means
no) and with what power, which of our bullets hit, which of its bullets hit us, and whether it hit a
wall. `energyChange` is the arithmetic of step 1, the other way round: from causes to symptom.

## The generator

```java
@Provide
Arbitrary<Double> shotOrNone() {
    return Arbitraries.frequencyOf(
        net.jqwik.api.Tuple.of(1, Arbitraries.just(0.0)),
        net.jqwik.api.Tuple.of(2, power()));
}

@Provide
Arbitrary<Interval> intervals() {
    return Combinators.combine(shotOrNone(), power().list().ofMaxSize(2),
            power().list().ofMaxSize(2), Arbitraries.of(true, false),
            Arbitraries.doubles().between(2.5, 8.0))
        .as(Interval::new);
}

@Provide
Arbitrary<List<Interval>> battles() {
    return intervals().list().ofMaxSize(25);
}
```

About a third of intervals have no shot, so the property also checks the ledger does not invent
one. A battle is up to 25 intervals in a row, because the ledger carries state from one scan to the
next, and a bug in clearing that state only shows up on the second interval.

## The property

```java
@Property
void recoversEveryShotFromAnyMixOfEvents(@ForAll("battles") List<Interval> battle) {
    EnergyLedger ledger = new EnergyLedger();
    double energy = 10_000;
    double speed = 5;
    ledger.scan(energy, speed);
    for (Interval i : battle) {
        for (double p : i.ourHits()) ledger.ourBulletHit(p);
        for (double p : i.theirHits()) ledger.enemyBulletHitUs(p);
        boolean wall = i.wall() && Math.abs(speed) > 2;
        double wallDamage = wall ? Math.abs(speed) / 2 - 1 : 0;
        energy += i.energyChange(wallDamage);
        speed = wall ? 0 : i.speed();
        EnergyLedger.Reading r = ledger.scan(energy, speed);
        if (i.shot() > 0) {
            assertTrue(r.shot(), "missed a shot of " + i.shot() + " in " + i);
            assertEquals(i.shot(), r.corrected(), 1e-9, "wrong power in " + i);
        } else {
            assertFalse(r.shot(), "invented a shot in " + i + ": " + r);
            assertEquals(0, r.corrected(), 1e-9);
        }
    }
}
```

Two things to notice. The start energy is 10,000, so the energy stays positive however many hits
the generator stacks up; the ledger does not care about the level, only the differences. And the
failure messages print the whole `Interval`, so when jqwik shrinks a failure to a minimal battle,
you read exactly which combination broke.

## The generator needs to know the rules too

Look at the wall line. A wall hit needs a robot going faster than it can brake, so the test only
simulates a wall when the previous speed was over 2. If the generator broke the physics, the
property would fail for a reason that has nothing to do with the ledger. A generator that builds
invalid worlds gives false alarms, and people learn to ignore them.

## Break it

Remove `- wall` from `corrected`, and run the property. jqwik finds a short battle that has a wall
hit and shrinks it to one interval. Put it back.

A second, smaller property checks that a ledger fed a steady energy and a steady speed infers no
wall damage.
