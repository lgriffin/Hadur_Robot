# Implement

Make the red tests green, one at a time, keeping the old behaviour as the default.

## Work in small steps

Take the failing tests in the order a reader would learn the feature, and for each one write the least code that passes it. Run the tests after every change.

Hadur's habit is one PR per stage. Yours is one commit per green test group. A step that breaks an earlier test is a step to undo, not to patch.

## Keep the shape

You built the hexagon in lab 04. Put each piece where the hexagon says.

| Piece | Goes in | Rule |
|---|---|---|
| A detector or a gate | `policy` (or a new package of your own) | plain values in, plain values out; no engine types. `policy` may depend on nothing else of Hadurling's (an ArchUnit rule since lab 11) |
| Movement or aiming maths | `move` or `gun` | pure and deterministic |
| Shadows, reflections, predictions | `physics` or `model` helpers | static methods; no state |
| Wiring | `Core` | the only place that knows about all of them; the gun, movement, ledger and memory packages may not use `policy` |
| Anything that touches Robocode | `hadurling-robot` | the adapter, never the core |

Hadur's own examples: `policy/RammerPolicy` decides, `move/RamEscape` moves, `HadurCore` wired them at 3.5. Since 3.6 the duel has its own brain, `duel.DuelController`, and that is where the wiring lives; Hadurling's `Core` plays both parts. `policy/MirrorDetector` decides, `move/MirrorDrive` plans and aims.

## Fail closed

The new behaviour needs every condition in your trigger to hold. Anything else gives the old behaviour.

```text
default = what Hadurling did before
new behaviour = trigger holds AND no veto AND no fault
```

Wrap the new code so an exception inside it falls back to the old behaviour for the rest of the round, as Hadur's `PostureGate` did (its successor since 3.6, `RoleResolver`, keeps the same veto). The `Guard` from lab 04 already protects the whole tick. Your wrapper protects the feature, so a bug in it never costs the whole tick.

## Gate on behaviour strong robots never show

This is the lesson of RAM-2's first cut (learning L-35). A rule meant for weak bots fired against nearly every strong robot and cost 5 points of share against the top 19. What fixed it was not a cleverer escape. It was a stricter trigger, found by replaying recorded battles and asking what strong robots never do.

You do not have the top 19. You have your regression set. For each opponent in it, look at your trigger and ask: could this bot make it fire? If yes, tighten it before you bench.

## Bounded and deterministic

- Any list has a cap, and a test that pushes past it (RES-2).
- No `java.util.Random`, no clock, no threads in the core. If you need pseudo-randomness, seed it from the round, as Hadur's `Duress` does.
- Break ties the same way every time: a larger mean distance, then the smaller change of heading, then the lower index.

## Mind the tick budget

If your feature does work per tick, say how much. RamEscape plays 24 headings by 2 orientations for 20 ticks, stops playing a candidate once it falls below the best so far, and skips the second orientation when no wall bent the first. That keeps a tick to about 0.2 ms. Use your lab 13 `TickBudget`: your feature should be one of the things shed at a high level.
