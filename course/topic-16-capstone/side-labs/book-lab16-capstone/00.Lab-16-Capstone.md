# Lab 16: Capstone, one feature end to end

You will give Hadurling one new feature and deliver it the way every Hadur stage was delivered: EARS requirements first, failing tests tagged with their IDs, the implementation, the guardrails green, a bench gate decided with an interval, and release notes. Then you open the real Hadur code for the same idea and compare.

This lab has no new theory. It uses everything from labs 01 to 13.

## Starting point

`course-labs/lab-13`, the last solution. It already has:

- three Maven modules: `hadurling-core` with no Robocode, `hadurling-robot` as the adapter, and `hadurling-bench` for battles
- ArchUnit rules, a determinism test and a replay test
- `docs/requirements.md` with EARS requirements `HL-1` to `HL-41`, tests tagged with them, and a traceability test that fails on an untested or unknown ID (it scans all three modules)
- a guess-factor gun on a KD-tree, a surfer, an energy ledger, saved profiles, a power policy and a tick budget
- a bench with a score share, a 95% interval and a paired A/B (`hadurling-bench`, run by hand; `mvn verify` runs no battle)

Make your working copy:

```sh
course-labs/tools/new-lab.sh 13 16
cd course-labs/lab-16
mvn -B verify
```

`new-lab.sh` copies `lab-13` to `lab-16` and renames the artifact IDs. Your new requirements start at `HL-42`. Without the repository, download [`start.zip`](./archives/start.zip) (it holds lab-13) and work in that folder instead.

The build must be green before you start. If it is not, fix that first. You cannot judge a change against a broken baseline.

There is no solution folder for this lab. Your repository is the answer.

## Objectives

- Choose a feature small enough to finish and real enough to need a bench
- Write its requirements in EARS, with stable IDs, before any code
- Write failing tests tagged with those IDs, then make them pass
- Keep ArchUnit, determinism, replay and traceability green
- Decide with a paired A/B and an interval whether the feature helps, does nothing or hurts
- Write release notes a stranger could act on
- Compare your version with the one Hadur shipped

## Steps

1. Choose a feature
2. Write the requirements
3. Failing tests first
4. Implement
5. Guardrails green
6. Bench gate
7. Release notes
8. Compare with Hadur

## What done looks like

- `docs/requirements.md` has your new rows, each with an ID, a pattern and a stage
- `mvn -B verify` is green, with no test skipped and the traceability test covering your IDs
- `docs/bench/` has a report of your A/B, with its conditions, your gate and the verdict
- `docs/releases/` has a release note
- You have written down what did not work

Allow a day. The bench in step 6 is the longest wait, so start it and write the release note while it runs.
