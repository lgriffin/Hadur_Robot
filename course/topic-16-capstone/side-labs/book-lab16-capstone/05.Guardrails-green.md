# Guardrails green

Green tests on your feature are not enough. Hadur's build also guards everything else, and an agent or a tired person forgets. Run all the guards, then break each on purpose.

## Run the whole build

```sh
mvn -B verify
```

Everything must pass with no test skipped.

| Guard | What it protects | If it fails |
|---|---|---|
| ArchitectureTest (lab 05, extended in labs 08 to 13) | no `robocode.*`, no `Random`, threads, files, channels, network or clock in the core; package directions, one pair of rules per package | move the code, or add a port |
| DeterminismTest | same inputs, same orders | find the hidden state, map order or clock |
| ReplayTest (lab 06) | a recorded battle gives the same orders | see below |
| Traceability (lab 07) | every ID has a test, no unknown tags | add the test, or fix the tag |
| Your properties | the fast code equals the slow twin | the code is wrong, not the property |

## The replay test is the one that bites

Your feature changes play, so the recorded battle may no longer reproduce. That is correct only when the feature's trigger fired in the recording.

1. Force the trigger off (a constant, a test flag). The replay must pass. If it does not, you changed the old behaviour. Find where.
2. Turn the trigger back on. If the replay still passes, the recorded opponent never triggered your feature, which is also fine and worth a sentence in your notes.
3. If the replay fails because the feature fired, regenerate the fixture on purpose, review the new transcript, and say why in the commit message. The scripted duel is made by `ScriptedBattle`; the command is in the lab 08 README:

   ```sh
   mvn -B test-compile
   java -cp hadurling-core/target/classes:hadurling-core/target/test-classes \
     hadurling.core.replay.ScriptedBattle hadurling-core/src/test/resources/replay/scripted-duel.txt
   ```

   If you also want a transcript of a real battle, the `HadurlingRecorder` robot from lab 06 writes one. If your scripted duel does not reach your trigger, extend `ScriptedBattle` so that it does, and say so.

Hadur's R9 commit says exactly this: "Replay fixtures re-recorded, duel sources re-pinned, round record gains fields 35-36." Three deliberate acts, each named. Compare: a silent change to a fixture is how drift hides.

## Add one rule of your own

Add an ArchUnit rule or a determinism check that fits your feature, so the next person cannot undo it by accident. Examples:

- if you add a package (a `posture` or a `shadow` package, say), give it the pair of rules that `knn`, `ledger`, `memory`, `port` and `policy` have: it depends on little, and few packages depend on it
- the shadow function is a leaf: it may depend only on `model` and `physics`, as Hadur's ledger may depend only on physics
- a test that two runs of your planner give equal plans

## Break each guard on purpose

Do this on a scratch branch and throw it away. Seeing each failure message once is how you learn to read it later.

1. Import `robocode.util.Utils` in your new class. ArchitectureTest should fail and name the class.
2. Call `System.nanoTime()` in it. Same.
3. Iterate a `HashMap` to choose a heading. Determinism should fail, maybe not every time. Think about why that is worse than failing every time.
4. Delete the test for one of your IDs. Traceability should fail and name the ID.
5. Add `@Tag("HL-99")` to a test. Traceability should fail on an unknown tag.

## Check yourself

- Do you know which guard failed in each experiment, and what it said?
- If your feature is off, is the replay byte for byte the old one?
- Can you say in one sentence what ArchUnit proves that the tests do not?
