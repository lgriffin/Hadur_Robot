# Failing tests first

Now write the tests, and make them fail for the right reason. A test that has never failed has never proved anything.

## One tag per requirement

Every test names the requirement it covers. The traceability test reads the tags.

```java
@Test
@Tag("HL-42")
@DisplayName("HL-42: a charge that stops at 150 px never starts the escape")
```

Hadur writes the `@DisplayName` as the requirement's own words. Failures then read like the sentence they break. Cucumber scenarios carry the same ID as `@HL-42`. A jqwik property uses jqwik's own `@Tag` from `net.jqwik.api`, not JUnit's, or the build skips it silently (testing.md).

## What to write

Aim for one test per row, and add these.

| Kind | What it checks | Hadur example |
|---|---|---|
| Example test | the main behaviour on one hand-made input | `PostureGateTest.meleeWhenTheGateHolds` |
| Boundary test | each threshold from either side | `RAM-2: a close pass that is not a charge (under four closing scans) confirms nothing` |
| Unwanted-case test | the false positive that must not fire | `MIR-1: an enemy orbiting us at 450 px (a surfer's path) never activates it` |
| Determinism test | the same inputs make the same output | `RAM-2: the same inputs choose the same heading (CORE-2)` |
| Property or model test | the fast code equals an obvious slow version | `BulletShadowsProperties.shadowsAreExactlyTheAnglesThatCollide` |
| State test | what a new round or a new opponent forgets | `MIR-1: a new round needs a new run; a new opponent forgets everything` |

Per option, a starting list.

- **Run from a rammer:** a stationary enemy never triggers; an enemy closing at 6 px/tick for four scans inside 120 px does; a detector that has seen one ram is not yet confirmed; the escape heading points away from the enemy; ties break the same way every time.
- **Bullet shadows:** a bullet fired straight at the enemy shadows the angle of its own line; no bullets in flight means no shadows; the property against brute force; danger at a shadowed angle is lower than at an unshadowed one.
- **Mirror detector:** an enemy at the reflection of where you were three ticks ago activates it with that lag; an enemy at the reflection of where you are now (lag 0) activates it with lag 0; an enemy orbiting at 450 px never does; it clears when the enemy stops following.
- **Posture gate:** two opponents and no sentry gives melee; one gives duel; a sentry gives duel, and the veto lasts until the next round; a fault vetoes melee for the round; sentry names are remembered and bounded.

## Red for the right reason

Create the classes with the simplest stub that compiles and returns the safe, old behaviour: `false`, `Posture.DUEL`, an empty list. Run the tests.

They should fail on an assertion, not on a compile error or an exception from your stub. Read each failure message. If a test fails for a reason that does not match its name, the test is wrong. Fix the test now, while there is no code to blame.

Count them: you should have as many red tests as there are rows, at least.

## Keep a record

Commit the red state with a message such as `capstone: failing tests for HL-42..HL-45`. A history that shows red, then green, is the evidence that the tests were written first.

## Check yourself

- Does each of your unwanted-case rows have a test that would fail if the trigger were too loose?
- Does any test depend on the real clock, a random number or the order of a `HashMap`? Remove it.
- Run `mvn -B verify`. Traceability should now be satisfied for your IDs, and the build red only on your new tests.
