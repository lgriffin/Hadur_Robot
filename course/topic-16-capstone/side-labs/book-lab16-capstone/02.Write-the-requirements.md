# Write the requirements

Requirements come before code. In Hadur the planner names an ID, and an implementer in a fresh session knows exactly what done means. You are both people, so write it as if someone else will build it.

## The five patterns

You met them in lab 07. A quick reminder with Hadur's own rows.

| Pattern | Shape | Hadur example |
|---|---|---|
| Ubiquitous | The system shall ... | CORE-1: The core shall not import any class from `robocode.*`. |
| Event | When ..., the system shall ... | MEM-1: When the first scan of a battle names an opponent, the core shall load the profile for that opponent's lineage key before producing orders for that tick. |
| State | While ..., the system shall ... | DIST-1: While our rolling hit rate exceeds the enemy's by 5 points or more, the distance policy shall reduce the target distance by 25 px per wave, not below 400 px. |
| Unwanted | If ..., then the system shall ... | WAVE-2: If a corrected energy drop is outside [0.1, 3.0], then the core shall not create a firing wave. |
| Optional | Where ..., the system shall ... | POW-1: Where the profile's gun tier is T0 and enemy energy exceeds 12, the gun shall fire power 3.0. |

## Write three to six rows

Add them to `docs/requirements.md` with the next free IDs (`HL-42` and up, in the style of the table: `| HL-42 | Pattern | Sentence |`). Each row has an ID, a pattern, one sentence and a stage (`C1` is fine).

A good set for any of the four options covers four things.

1. **The behaviour.** What the feature does when it is on.
2. **The trigger.** When it turns on. State it as a measurable condition on values the core already has, such as scans in a row, a distance, an energy level.
3. **The off switch.** When it turns off, and what the default is. Hadur's rule (DIAL-1) is that every policy keeps its conservative setting until the evidence is certain enough.
4. **The unwanted case.** What must never happen. For a detector this is the false positive: a strong robot that does something similar.

Examples of the fourth kind, from Hadur's tests of RAM-2 and MIR-1:

- a charge that stops at 150 px (a strong bot closing in) never starts the escape
- closing in on a robot under 20 energy (finishing it) confirms nothing
- two robots orbiting a point near the centre for 100 scans do not activate the mirror response
- an enemy sitting still at the centre never activates it

Those are requirements in disguise. Hadur's version of each came from a bench failure, and you can write yours now.

## Rules for a good row

- **One sentence a test can check.** If you cannot say what the test asserts, rewrite it.
- **Numbers in the row.** `120 px`, `two rounds`, `70%`. A threshold is part of the requirement, and a changed threshold is a reviewed change.
- **No solution words.** Say "keep a pursuing enemy furthest away over the next 20 ticks", not "use a for loop over 24 headings".
- **Bounded.** If it keeps a list, say how long it can get (RES-2).
- **Deterministic.** If it needs a choice among equals, say how ties break (CORE-2). If it needs randomness, it must be seeded.
- **Stable.** Once an ID is used it never changes meaning. If you change your mind, add a new ID.

## First red

Do not write any code yet. Run:

```sh
mvn -B verify
```

The traceability test from lab 07 should now fail, naming each new ID as "required but untested". That is the first red, and it proves the safety net works. Keep the output; you will paste it into your release note's history.

If the build stays green, your IDs are not being read. Check the table format against the existing rows (`HL-1` to `HL-41`) and fix the table.

## Check yourself

- Does every row have a trigger, or does it apply always?
- Is there at least one unwanted-case row?
- Could someone who has not seen your plan implement one row from its sentence alone?
