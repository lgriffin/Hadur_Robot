## ArchUnit for the new packages

Three new rules, one per relationship:

```java
@Test
@DisplayName("memory depends only on itself and the ports")
void memoryDependsOnPortsOnly() {
    classes().that().resideInAPackage("hadurling.core.memory..")
        .should().onlyDependOnClassesThat().resideInAnyPackage(
            "hadurling.core.memory..", "hadurling.core.port..", "java..")
        .check(core);
}
```

- `port` depends on nothing of Hadurling's but itself
- `memory` depends only on itself and the ports
- the gun, movement, ledger, model, physics and knn packages know nothing of memory or ports

Only `Core` joins them up. The robot module supplies the real store behind the port.

## Relaxing an old rule on purpose

Lab 05 banned all of `java.io` from the core, which was blunter than the intent. The codec uses
`DataOutputStream` to write into a byte array, which touches no disk. The rule now bans what reaches
the outside world:

```java
.should().dependOnClassesThat().resideInAnyPackage("java.nio.file..", "java.nio.channels..", "java.net..")
.orShould().dependOnClassesThat().haveFullyQualifiedName("java.io.File")
.orShould().dependOnClassesThat().haveFullyQualifiedName("java.io.FileInputStream")
...
```

Relaxing a guardrail is a decision, so it carries a comment that says why. Compare it with simply
deleting the rule, and notice that you still keep the part of its meaning that matters.

## The replay fixture

The replay fixture does **not** change in this lab. The scripted battle uses a `Core` without a
library, so its orders are the same. If your replay test fails here, something in your changes has
altered play when no library is present. Find it before you regenerate anything.
