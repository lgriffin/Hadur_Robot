# The live-loser loss sits in the 3.4 to 3.5.1 step

Finding: Hadur 3.5.1 scores 6.4 points below 3.4 on the 39 measurable live-loser opponents, and no later release recovers it.
Run: `docs/bench/a3/2026-10-06_ll-351v34.md` (R3), read with `docs/bench/local/2026-10-07_live-loser-bisect.md`
Raised: 2026-10-07

## 5 Whys

1. Why is 3.5.1 below 3.4 on the live losers? R3 (3.5.1 minus 3.4, 8 seeds, 39 opponents) is -6.37, opponent-clustered interval [-9.39, -3.36], with 14 of 39 opponents down after Holm and none up. R6 (3.8.5 minus 3.4) is -6.74, so the gap is still there in the newest release.
2. Why is it this step and not a later one? R1 (3.7 minus 3.5.1) is level at -0.35 and R2 (3.8.5 minus 3.7) is not resolved at -0.79 with an interval touching zero, so later releases neither widen nor close the gap. The three steps add to about -7.5 against R6's measured -6.74, within the intervals.
3. Why is it not CPU cost? R6 is down at the owner's CPU constant with about 11 skipped turns per battle on both sides. The tight runs (constant 400000) put both builds near 30% score share, so their level or positive signs are a floor effect and cannot say whether 3.4 is faster per turn.
4. Why can the bench not say which change inside 3.5.1 did it? The bisect runs whole releases. No per-commit run between v3.4 and v3.5.1 exists, so the cause inside that step is not measured.
5. Why is even the size of the loss uncertain? The live-loser set was chosen because 3.8 and 3.8.5 scored under 3.4 live, from one to three live battles per pairing, so part of the set is selected on 3.4's luck. The only unselected comparison with 3.4 (3.8 against 3.4 on the leak set) is level at +0.66, and no 3.5.1-against-3.4 run exists on an unselected set.

Chain ends at: the bench has no unselected set run for 3.5.1 against 3.4 and no per-commit bisect inside the release step, so selection luck and cause are not separated.
